# 订单兑换信息：账号角色自动匹配

订单确认页先选游戏服务器，再显示数据库中当前账号在该服的游戏角色。取消手填角色名及备注输入，订单详情也不展示备注。保持 Vanguard Armory 现有布局和配色；用户只能为自己的角色购买。

## 数据与接口

- 新增 `game_characters`：id、user_id、server、character_name、created_at；账号/服务器唯一，账号外键限制删除。角色名为 2–10 字。
- `GET /api/orders/character?server=star_1`：只允许已登录且未冻结的普通用户，从认证身份取得 user_id，返回 `{character: {id,server,character_name}}`；无角色返回 `{character:null}`。不接受外部 user_id，响应不可缓存。
- `POST /api/orders` 新请求只包含 request_id、items、server、character_id。角色 ID 是用户确认的对象，不能作为授权凭证；服务器在事务内使用 user_id + server 锁定角色并比较 ID，无匹配角色时返回 409/10007。
- 订单新增可空 `character_id` 外键，新订单写入角色 ID、当时名称和服务器快照。历史订单保持 NULL 关联和原名称，不猜测匹配。角色改名后历史名称不变；重试原订单先读取回执，不会依赖当前角色名重新计价或扣库。
- 金额、库存及购物车规则沿用现有逻辑。锁定顺序为购物车 → 提交回执 → 角色 → 购物车行 → 装备（按 ID），角色与订单、快照、库存和购物车删除一起确定。

## 页面与恢复

切服立即清除旧角色，查询中、查询失败或没有角色均不能提交；查询失败提供重试按钮。角色查询由 orders Store 管理，AbortController、请求代次、会话 revision 和账号身份共同隔离迟到响应。退出、切账号或离开确认页会清理角色状态。

新提交只携带角色 ID，不从页面接收角色名或备注。本地 key 仍为 `game_store.checkout.<userId>.v1`，新记录的 envelope.version 为 2；保留读取旧 version=1 的能力，避免升级时丢失未决提交。已经存在的旧订单仍可通过原编号恢复或重放；尚未创建的旧请求返回明确的升级冲突，原记录先标记拒绝，用户重新确认后采用新流程。不会把旧角色名偷偷换成新角色后沿用同一编号。

数据库 remark 字段保留以保护旧数据；新订单为 NULL。当前订单接口不返回备注，前端无备注入口或展示。

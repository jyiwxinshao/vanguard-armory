# 第五阶段：订单与模拟支付

本阶段接入订单确认、创建、模拟支付、取消与订单历史，形成「购物车 → 确认订单 → 创建订单 → 模拟支付」的完整流程。前台继续使用 **VANGUARD ARMORY / 先锋军械库** 品牌与 [DESIGN.md](DESIGN.md) 视觉体系，认证、装备浏览、购物车与登录合并等既有能力保持不变。

数据库在六张业务表之外新增一张 `order_requests`，用于下单请求的持久幂等去重；`orders` 与 `order_items` 沿用原设计，分别保存订单主记录与下单时的装备快照。

## 功能范围

- 购物车整车结算进入订单确认页，填写游戏角色名、服务器和可选备注。
- 创建订单时由服务器重新读取购物车、装备价格与库存，拒绝前端传入的最终金额；成功后在事务中扣减库存、写入订单与快照明细，并清空本次已购买的购物车条目。
- `request_id + order_requests` 幂等：同一提交编号与同一内容重复请求返回同一订单，不重复扣库存、不重复生成订单。
- 状态流转：`pending → paid`（模拟支付）、`pending → cancelled`（取消并返还库存）；`paid → completed` 预留给后续管理端，当前未开放用户接口。
- 取消订单按快照明细返还库存；重复取消已取消订单不再次返还。
- 支付与取消竞争时只有一个状态转换成功，库存与状态保持一致。
- 订单列表支持状态、创建时间区间和 10/20/50 分页；仅返回当前用户自己的订单。
- 订单详情展示快照明细、兑换信息、商品总额、优惠和应付/实付金额，并按状态显示支付或取消操作。

## 后端行为

### 接口

以下接口均要求 `active` 普通用户；未登录返回 401，管理员访问返回 403。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/orders` | 创建订单；返回订单、`request_id`、`replayed` 和最新购物车 |
| GET | `/api/orders` | 按状态、创建时间区间、分页查询本人订单 |
| GET | `/api/orders/:id` | 查询本人订单及快照明细 |
| GET | `/api/orders/by-request/:requestId` | 按提交编号恢复本人订单结果 |
| PUT | `/api/orders/:id/pay` | `pending → paid`，记录支付时间，不发起真实扣款 |
| PUT | `/api/orders/:id/cancel` | `pending → cancelled`，返还库存并记录取消时间 |

### 校验

- 角色名去除两端空白后 2–10 个 Unicode 字符，不含控制字符；服务器必须是元数据中的合法值；备注最多 200 个字符。
- 确认条目为 1–100 项，每项包含 `cart_item_id、equipment_id、quantity、expected_price`；`cart_item_id` 与 `equipment_id` 均不可重复。
- `quantity` 为 1–9999，`expected_price` 为 1–1000000；`expected_price` 只用于校验变价，不作为计价来源。
- 订单 ID 为正整数；列表分页为 10/20/50，状态为 `pending/paid/cancelled/completed` 之一。
- 时间区间使用带 `Z` 的 ISO 8601 UTC 时间，后端按左闭右开处理；结束时间早于开始时间返回 422。

### 创建订单事务

1. 校验身份与输入，计算提交内容的 `payload_hash`。
2. 锁定用户 `carts` 行；写入 `order_requests` 回执并读取锁定，实现幂等。
3. 校验请求条目与当前购物车逐项一致（ID、装备、数量），不一致返回 409/10007。
4. 按装备 ID 顺序锁定装备行，校验在售、库存和确认价格，任一失效返回对应错误。
5. 以数据库当前价格计算总额，扣减库存（使用带 `stock >= quantity` 条件的更新）。
6. 写入 `orders` 与 `order_items` 快照，删除本次已购的购物车条目，更新购物车时间。
7. 提交事务；任何一步失败整体回滚，库存、订单、回执和购物车都保持提交前状态。

### 幂等与回执

- 客户端在确认页持久化一个 UUID v4 `request_id`；重试和刷新沿用同一编号与不可变提交内容。
- `order_requests` 以 `request_id` 为主键，`order_id` 唯一；同一 `request_id + payload_hash` 重复请求返回 `replayed: true` 和原订单。
- 同 ID 换账号或换内容返回 409/10012；用户身份从 JWT 读取。
- 延迟重试、断网后恢复和并发重复提交都不会重复下单或重复扣库存。

### 支付、取消与竞争

- 支付只允许 `pending → paid`，记录 `payment_time`，不修改库存。
- 取消只允许 `pending → cancelled`，按 `order_items` 快照逐项加回库存，记录 `cancelled_at`。
- 重复支付或重复取消返回当前订单，不改变时间戳、不重复返还库存。
- 支付与取消并发时通过订单行锁和状态检查，只有一个操作成功；另一个读取新状态后返回 409/10008。
- 返库存失败或行锁竞争会整体回滚并返回 409/10009，订单保持原状态。

## 前端行为

### 订单 Store

`useOrdersStore` 维护 `items、total、detail、listLoading、detailLoading、acting、listError、detailError、confirmation、draft、checkoutLoading、checkoutError、checkoutNotice`，提供：

- `loadList(params)`：订单列表加载，保留请求版本避免旧响应覆盖新结果。
- `loadDetail(id)`：订单详情加载与校验。
- `action(name)`：模拟支付或取消，成功后用服务器返回的最新订单覆盖详情。
- `loadCheckout()`：从购物车生成确认清单。
- `submit(values)`：持久化 `request_id` 后提交，成功或明确业务拒绝后再处理本地草稿。
- `recover()`：按 `request_id` 查询订单结果并恢复。
- `reconfirm()`：明确拒绝后放弃旧草稿，重新确认购物车。

`useOrdersStore` 在账号切换、退出或登录状态变化时清空列表、详情、确认与草稿，旧请求不能写入新账号页面。

### 本地下单草稿

`client/src/utils/checkout-storage.js` 以 `game_store.checkout.<userId>.v1` 保存 `pending/rejected` 两种草稿，包含不可变的 `request_id` 与提交内容。只有明确创建成功后才清除；网络失败、结果未知时保留同一编号用于恢复，避免自动重发导致重复下单。

### 页面

- `Checkout.vue`：订单确认页，展示整车清单、兑换信息、应付金额；支持恢复、重试和重新确认。
- `Orders.vue`：订单列表，状态/日期/每页筛选，分页与详情入口。
- `OrderDetail.vue`：订单详情、快照明细、应付/实付金额、支付与取消操作。
- `OrderItems.vue`：订单装备明细组件，区分购物车实时数据与订单快照。
- 顶部「我的订单」接入 `/orders`，购物车「去结算」跳转 `/checkout`。
